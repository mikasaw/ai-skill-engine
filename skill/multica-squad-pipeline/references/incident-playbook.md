# 事故处置手册：串台事故全程复盘（真实案例模板化）

真实案例：第三迭代 S2，agent 在**单据正确**（#2 index.html 收口）的情况下，
交付了完全无关的 726 行工具（match.py 对账），并以 `<污染commit>` 提交进 main。
本手册是该事故从发现到闭环的全流程模板。

## 第一步：发现（验收第一动作就是范围检查）

`git show --stat HEAD` —— 改动文件与单据范围不符（本单应只动 cache.py + test_incremental.py，
实际多了 match.py 等 4 个新文件）。

**立即停止正常验收流程**，进入事故模式：不 revert、不删文件、不动 main——先取证。

## 第二步：取证（固化证据链，四件套）

1. **单据是否被篡改**：`issue get <id>` 检查 description 是否仍是派发原文
   （本案：未篡改，仍是 #2 原文，不含 match.py 字样 → 排除"派错单"）；
2. **run 归属**：`issue runs <id>` 看 `attribution`（本案：agent_id = 我方 mdboard-dev、
   evidence.kind = issue_assignment、经正常编排链 → 排除"外人入侵"）；
3. **时间对齐**：污染 commit 的时间与 run completed 差 1 分钟 → 确认就是这一棒所为；
4. **引用物核实**：交付报告引用的关联单号（两个并不存在的单号）在工作区**不存在**
   → 坐实 agent 上下文串台/幻觉，而非另一条真实流水线。

四件套齐了再下结论。本案结论：**单据正确 + 编排正常 + 交付无关 = agent 跨单上下文污染**。

## 第三步：判 0 分不通过（证据进 issue）

verdict reasons 固化全部证据（单据状态/attribution/时间线/引用物核实结果），
处置要求写明"污染 commit 需项目主拍板"。**验收方不擅自改 main**——
revert/reset 是状态变更，归项目主裁定（本案用户选 A：revert）。

## 第四步：处置（选项模板）

| 选项 | 适用 |
|---|---|
| A：`git revert <污染commit>` | 污染与本流水线无关（推荐；内容仍可经历史追溯） |
| B：先移存内容再 revert | 污染物恰好是用户另一条线想要的功能 |
| reset --hard | 技能文档裁定为 anti-pattern：丢审计痕迹；确需时必须项目主拍板 |

revert 提交信息写明：污染原因 + 指向验收评论 + 恢复的基线（测试数）。
验证三件套：`git status --porcelain` 空、全量测试恢复基线、污染文件零踪迹
（`git ls-files | grep <特征>` exit 1）。

## 第五步：重派与加强验收

- 打回指引评论先在案 → `issue rerun <id>`（正确顺序）→ 重跑；
- 重跑交付的验收在原判据之上**加一条范围一致性复查**（防二次串台）；
- 产出物若仍有价值（如本案 match.py），提示用户可经 git 历史追溯、移独立单据另议。

## 第六步：根因治理（归项目主侧，仓库外）

- 根因 = 同一 agent 实例跨单上下文污染。治理 = instructions 整表替换（高危操作，
  按 pitfalls 表纪律：GET 全量 → 追加 → ≤1800 字符 → 回读核对）；
- 固化条款（本案实际落地文本）：
  1. 开工先核对单据范围，上下文残留记忆与单据冲突时以单据为准；
  2. 已 done 子单被再唤醒：只回报、不提交；
  3. 脏 worktree 开工守卫。

## 事故的"审计痕迹保护"（贯穿全程）

事故提交对（污染 `<污染commit>` + revert `<revert提交>`）**永久保留在历史**：
净零例外用最强证据放行（`git diff <前> <后>` 为空 + `tree(前)==tree(revert后)`）；
**任何 reset/rebase/amend 抹痕迹的提议 = BLOCKER**，停下回报项目主。
复审方应主动立此规矩——本案复审员先于所有人提出，被采纳为常规范式。
