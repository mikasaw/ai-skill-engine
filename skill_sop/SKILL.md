# mdboard 小队流水线 SOP（全角色共读）

> 配套角色 instructions 使用：instructions 是硬红线，本文件是详细作业手册。
> 冲突时以 issue 描述与 Architect 裁决为准，其次本文件，最后个人判断。

## 开工三守卫（每个任务开工前逐条执行）

1. **范围核对**：通读本 issue 描述，确认任务与你的角色契约一致；交付前自证交付物与单据一致。若与你上下文中残留的其他任务记忆冲突，一律以单据为准，忽略残留。
2. **脏 worktree 守卫**：`git status --porcelain` 非空即停手回报，不清理、不提交他人改动。
3. **再唤醒守卫**：已 done 的子单因验收评论被再次唤醒时，只回报现状（不重复工作），不修改代码、不产生新提交。

## 回报格式（硬性）

- 做了什么（对应编号 / 文件清单）；
- 跑过的命令与关键输出**原样粘贴**（pytest 结果行不得转述）；
- 当前 `git log --oneline`；
- 交付前自证：`git show --stat HEAD` 与单据范围一致（防串台）。

## 提交纪律

- 前缀：修复 `fix(#N)`、测试 `test:`、杂务 `chore:`；不复用已完成迭代的编号段；
- 事故提交对（污染 + revert）**永久保留**：不 amend、不 reset、不 rebase；
  净零例外放行标准：`git diff <事故前> <revert后>` 为空（可加树对象同一加强）；
- 基线测试数**只增不减**、无 skipped；
- 冻结边界不得顺手扩大：无第三方运行时依赖、无内容哈希、无递归删除、`parse_dir` 单层；
- **变异自证**：新增防回归用例必须贴出"删除被测行为后该用例失败"的 pytest 输出。

## 验收 / 复验纪律（verifier / reviewer）

- **独立复跑，不复读自报**——任何"开发说 PASS"必须亲手复跑后才接受；
- 至少一个**真实工件最恶劣场景**核验（造最坏输入，查实际产物字节/退出码/stderr）；
- 变异自证需**第三方复核**：评审方亲手做一次变异，不只看 dev 贴的输出；
- 发现判据自身有坑：停手回报 Architect 裁定，不将错就错、不自行解释；
- 范围外隐患：带行号留档（"仍存在、本轮范围外"），不修也不据此判不通过；
- **不可达防御代码 = MAJOR**：给守卫加分支前必须证明该分支独立可达。

## stage 屏障与提升协议

- 子单交付方落 `in_review`，**不得自行置 done**；done 归验收方，done 才关闭 stage 屏障；
- 提升下一棒 = `issue assign` + `issue status <id> todo` **两步**（backlog 不会被拾取，
  这是并发防护不是故障；只 assign 不提升 = 永远停在 backlog）；
- 除 Stage 1 外的子单创建时**不带 assignee**；
- 任何 reset / rebase / amend 抹事故审计痕迹的提议 = **BLOCKER**，停手回报项目主。

## 判据歧义

判据文字与事实冲突时：停下回报 Architect，附最小复现与实际输出；
不自行解释、不将错就错、不因判据有误而隐瞒真实结果。
